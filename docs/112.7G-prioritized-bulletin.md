## 2. Objetivo

O Prioritized Bulletin responde exclusivamente:

> **Como organizar deterministicamente, para um único contexto científico personalizado, uma coleção de eventos já avaliados pelo Interest Engine?**

O componente recebe eventos associados aos respectivos resultados do Interest Engine, valida o lote, forma grupos deduplicados, escolhe representantes, preserva a explicabilidade dos membros, ordena os itens e produz um modelo de conhecimento neutro.

---

## 3. Escopo

O 112.7G deve:

- validar associações `Event`–`InterestResult`;
- validar homogeneidade do contexto científico;
- rejeitar avaliações duplicadas do mesmo evento e contexto;
- projetar entradas para candidatos internos imutáveis;
- validar conteúdo e timestamps utilizados;
- deduplicar eventos por identidade conservadora;
- ordenar todos os membros por chave total;
- selecionar o representante de cada grupo;
- preservar a explicabilidade de cada membro;
- agregar revisão humana por OR;
- ordenar os itens finais;
- agrupar por `InterestPriority`;
- produzir seções com identidade estrutural;
- produzir `PrioritizedBulletin` imutável;
- serializar o modelo por contrato canônico próprio;
- produzir o mesmo resultado para o mesmo request e configuração.

## 7. Princípios e invariantes

1. Um request produz exatamente um boletim.
2. Um boletim representa exatamente um contexto científico.
3. Contexto nunca é inferido de lote vazio.
4. `InterestResult` é autoridade exclusiva para prioridade científica.
5. `Event` é autoridade exclusiva para conteúdo e timestamps.
6. Nenhum score ou nível é recalculado.
7. Nenhuma reason ou match é reinterpretada.
8. Cada entrada possui associação explícita Event–InterestResult.
9. Cada avaliação lógica aparece no máximo uma vez.
10. Deduplicação não usa texto ou semântica aproximada.
11. Cada grupo possui representante determinístico.
12. Todos os membros permanecem auditáveis.
13. Revisão humana é agregada conservadoramente.
14. Cada item pertence a exatamente uma seção.
15. Seções possuem identidade estrutural.
16. Nenhuma seção vazia é emitida.
17. Nenhum limite causa truncamento silencioso.
18. Nenhum timestamp runtime é gerado.
19. O resultado não contém apresentação ou publicação.
20. A ordem original de `entries` não altera o resultado.

## 9. API pública

```python
class PrioritizedBulletinEngine:
    def __init__(
        self,
        config: PrioritizedBulletinConfig,
    ) -> None:
        ...

    def build(
        self,
        request: PrioritizedBulletinRequest,
    ) -> PrioritizedBulletin:
        ...
```

`build()` é:

- síncrono;
- puro em relação ao request e à configuração;
- determinístico;
- sem I/O;
- sem efeitos colaterais;
- independente de ordem de entrada;
- seguro para chamadas repetidas.

O construtor revalida a configuração materializada antes de armazená-la:

- estrutura e tipos do modelo;
- versão suportada;
- políticas V1;
- `priority_order`;
- `section_titles`;
- limites.

Ao receber uma configuração já materializada, o construtor converte falha estrutural ou semântica de revalidação em `PrioritizedBulletinConfigError`. Versão programática incompatível lança diretamente `PrioritizedBulletinVersionError`.

Construção direta inválida de `PrioritizedBulletinConfig(...)` produz `ValidationError` antes de existir argumento materializado para o engine, conforme a fronteira Pydantic da seção 48.

Um engine inválido nunca é construído. Portanto, validação de configuração precede qualquer chamada de `build()` e não compete com erros do request.

## 11. PrioritizedBulletinContext

```python
class PrioritizedBulletinContext(BaseModel):
    model_config = ConfigDict(
        strict=True,
        frozen=True,
        extra="forbid",
    )

    researcher_id: str
    profile_version: str
    taxonomy_version: str
    interest_algorithm_version: str
    interest_config_version: str
```

Todos os campos são obrigatórios, inclusive em request vazio.

Regras para cada string:

- deve ser `str`;
- recebe trim de whitespace nas bordas na fronteira do modelo;
- deve permanecer não vazia após trim;
- o valor armazenado é o valor normalizado;
- whitespace interno é preservado;
- nenhuma string é convertida para lowercase;
- versões não são semanticamente interpretadas;
- igualdade usa comparação exata da string normalizada.

`researcher_id` corresponde literalmente ao tipo público `InterestResult.researcher_id`. Não existe parsing como UUID.

`taxonomy_version`:

- é fornecida pelo caller;
- representa a Taxonomia associada ao perfil usado pelo orquestrador;
- não é derivada de `InterestResult`;
- não é lida da configuração do 112.7G;
- não pode ser verificada contra `InterestResult`, pois o campo não existe upstream.

Essa limitação de proveniência é vinculante e explícita.

## 12. PrioritizedBulletinEntry

```python
class PrioritizedBulletinEntry(BaseModel):
    model_config = ConfigDict(
        strict=True,
        frozen=True,
        extra="forbid",
    )

    event: Event
    interest_result: InterestResult
```

A imutabilidade é superficial em relação ao `Event`, cujo contrato atual não é frozen.

`PrioritizedBulletinEntry` é frozen somente quanto à substituição de seus próprios atributos. O `Event` é um contrato upstream de entrada e pode conter listas, mappings e outras estruturas mutáveis. Essa exceção não reduz a exigência de imutabilidade profunda dos modelos de configuração e saída pertencentes ao 112.7G.

No início de `build()`, todos os campos utilizados são copiados para candidatos internos imutáveis.

A projeção defensiva desta etapa é uma captura de valores, sem validação semântica. Associação, contexto, revisão, scores, textos e datetimes são validados posteriormente na ordem vinculante.

A saída não mantém referência mutável ao `Event` recebido.

Depois do retorno de `build()`, qualquer mutação posterior no `Event` original não altera o `PrioritizedBulletin` já construído.

Mutação concorrente das entradas durante `build()` viola o contrato do caller.

## 13. Associação Event–InterestResult

Para cada entrada:

```text
event.id presente
event.id UUID válido
interest_result.event_id presente
interest_result.event_id UUID canônico
str(event.id) == interest_result.event_id
```

Qualquer falha produz diretamente:

```text
PrioritizedBulletinAssociationError
```

O engine não procura Event ou InterestResult ausente.

Uma entrada contém os dois lados obrigatórios da associação.

---

## 14. Homogeneidade do request

Para request não vazio, cada `InterestResult` deve satisfazer:

```text
interest_result.researcher_id
== context.researcher_id

interest_result.profile_version
== context.profile_version

interest_result.algorithm_version
== context.interest_algorithm_version

interest_result.config_version
== context.interest_config_version
```

`taxonomy_version` não participa da comparação porque não existe em `InterestResult`.

Qualquer divergência produz:

```text
PrioritizedBulletinContextMismatchError
```

O lote inteiro falha. O engine não particiona automaticamente o request.

## 15. Identidade e UUIDs canônicos

UUID canônico público:

```text
lowercase
com hífens
sem braces
sem prefixo
```

Forma normativa:

```python
canonical_id = str(uuid_value)
```

Para `interest_result.event_id`:

- parsing como UUID deve ser bem-sucedido;
- a string recebida deve ser exatamente igual a `str(parsed_uuid)`;
- forma parseável, mas não canônica, é inválida.

Para cada entrada validada, a chave de avaliação é:

```text
(
    interest_result.event_id,
    interest_result.researcher_id,
    interest_result.profile_version,
    interest_result.algorithm_version,
    interest_result.config_version,
)
```

Repetição dessa chave produz `PrioritizedBulletinDuplicateEntryError` antes da deduplicação por identidade estruturada.

## 17. PrioritizedBulletinItem

```python
class PrioritizedBulletinItem(BaseModel):
    model_config = ConfigDict(
        strict=True,
        frozen=True,
        extra="forbid",
    )

    representative_event_id: str
    member_event_ids: tuple[str, ...]

    title: str
    summary: str | None
    scientific_area: str | None
    category: str | None
    occurred_at: datetime | None
    validated_at: datetime | None

    relevance_score: float
    significance_score: float
    significance_level: EventSignificance
    priority_score: float
    priority_level: InterestPriority

    matched_concepts: tuple[InterestConceptMatch, ...]
    matched_research_lines: tuple[ResearchLineMatch, ...]
    reasons: tuple[str, ...]

    requires_human_review: bool
    members: tuple[PrioritizedBulletinMember, ...]
```

Regras:

- representa exatamente um grupo deduplicado;
- `member_event_ids` inclui o representante;
- `representative_event_id == member_event_ids[0]`;
- não existem IDs duplicados em `member_event_ids`;
- `members` possui exatamente os mesmos IDs;
- `members` segue a mesma ordem de `member_event_ids`;
- `members[0].event_id == representative_event_id`;
- campos de score, nível, matches e reasons de primeiro nível pertencem somente ao representante;
- `title`, `summary`, `scientific_area` e `category` pertencem somente ao snapshot normalizado do Event representante;
- `occurred_at` e `validated_at` pertencem somente ao snapshot UTC normalizado do Event representante;
- `members` preserva a explicabilidade de todos os eventos;
- `requires_human_review` é OR dos membros;
- o `requires_human_review` agregado do item é campo público de curadoria e não participa da chave de ordenação do item;
- a quantidade do grupo é `len(member_event_ids)`;
- não existe `source_count`.

## 21. Política de datetime

`occurred_at` e `validated_at` podem ser `None`.

Quando presentes:

- devem ser `datetime` timezone-aware;
- `tzinfo` não pode ser `None`;
- `utcoffset()` não pode ser `None`;
- são convertidos para UTC;
- o instante absoluto é preservado;
- microssegundos são preservados;
- não existe truncagem;
- não existe arredondamento;
- offset original não é preservado na saída.

Datetime inválido produz `PrioritizedBulletinInputError`.

Na ordenação descendente:

- valor presente vem antes de `None`;
- instante UTC mais recente vem primeiro.

Serialização pública:

```text
YYYY-MM-DDTHH:MM:SS.ffffffZ
```

## 22. Política numérica

Os scores públicos permanecem `float`:

- `significance_score`;
- `priority_score`;

- não requantizar;
- não arredondar;
- não recalcular;
- não alterar níveis;

- NaN é inválido;

- `-0.0` é normalizado para `0.0` na projeção pública;
- todo outro valor finito é preservado numericamente.

Falha durante `build()` produz `PrioritizedBulletinInputError`.

## 23. Human review

Para cada entrada, o valor esperado é calculado exclusivamente a partir do snapshot de `Event` recebido:

```text
expected_requires_human_review =
    True
    se event.pipeline_status == PipelineStatus.ESCALATED
    senão event.requires_human_review

interest_result.requires_human_review
== expected_requires_human_review
```

Divergência produz:

```text
PrioritizedBulletinReviewMismatchError
```

Antes do cálculo:

1. `event.pipeline_status` deve ser uma instância válida de `PipelineStatus`;
2. `event.requires_human_review` deve ser bool estrito;
3. `interest_result.requires_human_review` deve ser bool estrito.

Falha estrutural nesses três campos produz `PrioritizedBulletinInputError` antes da comparação de review. Depois dessas validações, divergência do valor esperado produz `PrioritizedBulletinReviewMismatchError`.

Consequências vinculantes:

- Event `ESCALATED` com `event.requires_human_review=False` e `interest_result.requires_human_review=True` é válido;
- Event `ESCALATED` com `interest_result.requires_human_review=False` produz `PrioritizedBulletinReviewMismatchError`;
- Event não `ESCALATED` exige igualdade entre `interest_result.requires_human_review` e `event.requires_human_review`;
- o 112.7G não altera o Event;
- o 112.7G não recalcula score ou nível.

No grupo:

```text
item.requires_human_review = any(
    member.requires_human_review for member in members
)
```

Cada `member.requires_human_review` é copiado do valor já validado de `interest_result.requires_human_review` da entrada correspondente.

Revisão humana:

- não altera scores;
- não altera níveis;
- não decide publicação;
- o valor de cada candidato é o primeiro tie-breaker depois de `priority_score` na ordenação dos membros e na escolha do representante;
- na ordenação dos itens, o tie-breaker é exclusivamente `representative.requires_human_review`;
- o OR agregado em `item.requires_human_review` não participa da ordenação;
- é preservada para a curadoria.

## 24. Deduplicação

A deduplicação V1 é conservadora e baseada somente em identidade estruturada.

Não usa:

- título normalizado;
- resumo;
- categoria;
- similaridade textual;
- similaridade semântica;
- fuzzy matching;
- embeddings;
- LLM;
- heurísticas editoriais.

Eventos semanticamente semelhantes sem `primary_claim_id` comum permanecem distintos.

---

## 25. Chave de deduplicação

Quando `event.primary_claim_id` estiver presente:

```text
(
    "PRIMARY_CLAIM",
    str(event.primary_claim_id),
)
```

Quando estiver ausente:

```text
(
    "EVENT_ID",
    canonical_event_id,
)
```

`primary_claim_id` deve ser UUID válido. Sua forma canônica é lowercase com hífens, produzida exclusivamente por `str(UUID)`.

Não existe normalização textual adicional.

---

## 26. Escopo global da deduplicação

- deduplicação ocorre globalmente no request;
- ocorre antes da criação das seções;
- um grupo aparece em exatamente uma seção;
- não existe deduplicação por seção;
- grupos são formados depois das validações de associação, contexto, duplicidade e revisão.

---

## 27. Ordenação total

Chave total de um registro representativo, nesta ordem:

1. `priority_score` DESC;
2. `requires_human_review` DESC;
3. `relevance_score` DESC;
4. `significance_score` DESC;
5. `occurred_at` DESC, presente antes de `None`;
6. `validated_at` DESC, presente antes de `None`;
7. `event_id` ASC.

Aplicação vinculante:

- cada candidato usa seus próprios valores para ordenar membros;
- o primeiro candidato segundo essa chave é o representante;
- cada item usa exclusivamente os valores de seu representante para todos os sete componentes;
- no segundo componente da chave do item, `requires_human_review` significa `representative.requires_human_review`;
- `item.requires_human_review`, agregado por OR, não substitui o valor do representante e não participa da chave.

Os scores são os floats públicos válidos recebidos do 112.7F.

Nenhum arredondamento adicional participa da comparação.

`InterestPriority` e `EventSignificance` não são tie-breakers separados porque são derivados de scores upstream.

---

## 28. Ordenação dos membros

Todos os candidatos de um grupo são ordenados pela chave total da seção anterior antes da projeção pública.

Depois da ordenação:

- `member_event_ids` segue essa ordem;
- `members` segue essa ordem;
- o primeiro candidato é o representante;
- a ordem não depende da entrada.

`PrioritizedBulletinMember` não precisa carregar timestamps porque a ordenação ocorre sobre o candidato interno completo.

---

## 29. Seleção do representante

O representante é o primeiro candidato após aplicação da chave total.

Invariantes:

```text
representative_event_id == member_event_ids[0]
members[0].event_id == representative_event_id
```

Não existe seleção por primeira ocorrência.

Não existe merge ou recálculo de score.

---

## 30. Ordenação dos itens

Itens deduplicados são ordenados pela mesma chave total, usando exclusivamente os dados do representante em todos os componentes.

Para a ordenação do item:

```text
ordering_requires_human_review = representative.requires_human_review
```

O campo público `item.requires_human_review` permanece o OR dos membros e nunca é lido pela rotina de ordenação.

O último desempate é `representative_event_id ASC`.

Consequentemente, a ordenação dos itens é total e independente da ordem do request.

Exemplo normativo:

```text
representative.requires_human_review = False
outro membro.requires_human_review = True

item.requires_human_review = True
ordering_requires_human_review = False
```

O item preserva `True` para curadoria por causa do OR, mas é ordenado com `False`, que é o valor do representante. Nenhum score é alterado ou recalculado.

## 42. Loader público

```python
def load_prioritized_bulletin_config(
    path: str | Path,
) -> PrioritizedBulletinConfig:
    ...
```

Módulo:

```text
sentinela/prioritized_bulletin/config.py
```

Regras:

- leitura UTF-8 estrita;
- parsing YAML seguro;
- exatamente um documento;
- raiz obrigatoriamente mapping;
- documento vazio rejeitado;
- raiz null rejeitada;
- duplicate keys rejeitadas em qualquer nível;
- `algorithm_version` é inspecionada sem coerção depois do parsing seguro e da detecção de duplicate keys;
- quando `algorithm_version` estiver presente como string canônica, compatibilidade de versão é validada antes da normalização e validação dos demais campos;
- o mapping YAML de `section_titles` pode aparecer em qualquer ordem;
- as chaves de `section_titles` são validadas antes da ordenação;
- `section_titles` é normalizado para `tuple[PrioritizedBulletinSectionTitle, ...]` exatamente na ordem de `priority_order`;
- validação final pelo modelo estrito;
- validação semântica depois do modelo.

Parsing YAML seguro significa:

- tags específicas de objetos Python são rejeitadas;
- construtores capazes de instanciar objetos ou invocar callables são rejeitados;
- nenhum construtor arbitrário é executado;
- nenhum payload altera filesystem, processo, ambiente, rede ou qualquer outro estado externo;
- a rejeição ocorre como falha YAML normalizada para `PrioritizedBulletinConfigError`.

Fixtures normativas compatíveis com PyYAML para comprovar rejeição, tratadas somente como texto e nunca executadas:

```yaml
algorithm_version: !!python/name:os.system
```

```yaml
algorithm_version: !!python/object/apply:os.system ["echo forbidden"]
```

A primeira fixture cobre tag Python insegura. A segunda cobre construtor inseguro com tentativa declarativa de invocação. O teste deve apenas fornecer o texto ao loader seguro e comprovar a rejeição; não executa nem autoriza executar o callable referenciado.

As únicas transformações permitidas antes da validação strict são, exaustivamente:

1. string canônica para `PrioritizedBulletinGroupingPolicy`;
2. string canônica para `PrioritizedBulletinDeduplicationPolicy`;
3. strings canônicas de `priority_order` para `InterestPriority`;
4. chaves textuais de `section_titles` para `InterestPriority`;
5. valores textuais de `section_titles` para `PrioritizedBulletinSectionTitle` com a prioridade correspondente;
6. listas YAML documentadas para tuplas;
7. mapping de `section_titles` para tupla ordenada exatamente conforme `priority_order`.

Nenhuma outra coerção ou normalização é permitida. São explicitamente proibidos:

- bool para int;
- string numérica para int;
- número para string;
- enum desconhecido;
- valor textual com casing alternativo;
- alias não documentado;
- qualquer transformação não enumerada acima.

A política de duplicate keys é aplicada separadamente a cada mapping do schema. Na V1, os mappings YAML são a raiz e `section_titles`; não existe outro mapping aninhado. Quando o parser fornecer uma exceção original de duplicate key, ela é preservada em `__cause__` de `PrioritizedBulletinConfigError`.

Toda falha pública do loader produz `PrioritizedBulletinConfigError` com uma das mensagens exatas abaixo. `str(error)` é exatamente a mensagem indicada, sem prefixo, sufixo ou interpolação.

| Categoria | Mensagem pública exata | Aplicabilidade | Causa |
|---|---|---|---|
| Arquivo inexistente | `prioritized bulletin configuration file not found` | caminho inexistente ou arquivo esperado não localizado | exceção original em `__cause__`, quando disponível |
| Falha de leitura | `failed to read prioritized bulletin configuration` | falha de leitura não classificada como arquivo inexistente ou permissão negada; inclui decodificação UTF-8 inválida | exceção original em `__cause__` |
| Permissão negada | `permission denied while reading prioritized bulletin configuration` | acesso ao arquivo negado | exceção original em `__cause__` |
| YAML malformado | `invalid prioritized bulletin configuration YAML` | erro sintático ou estrutural do parser YAML, incluindo múltiplos documentos | exceção original do parser em `__cause__` |
| Duplicate YAML key | `duplicate key in prioritized bulletin configuration YAML` | duplicate key na raiz, em `section_titles` ou em qualquer mapping aninhado do schema V1 | exceção original do parser ou detector em `__cause__`, quando disponível |
| Tag ou construtor YAML inseguro | `unsafe YAML construct in prioritized bulletin configuration` | tag não permitida, construtor arbitrário, objeto Python ou construção rejeitada pelo parsing seguro | exceção original em `__cause__`, quando disponível |
| Estrutura de configuração inválida | `invalid prioritized bulletin configuration structure` | raiz não mapping, documento vazio ou null, campo obrigatório ausente, campo extra, tipo ou valor inválido, enum desconhecido, limite inválido, `section_titles` incompatível, normalização proibida, validação Pydantic ou invariante sem categoria mais específica | exceção técnica em `__cause__`, quando existir |
| Versão incompatível no loader | `unsupported prioritized bulletin configuration version` | `algorithm_version` estruturalmente válida, mas incompatível | `PrioritizedBulletinVersionError` em `__cause__` |

Precedência obrigatória de categorização da mensagem pública:

1. arquivo inexistente;
2. permissão negada;
3. outra falha de leitura;
4. tag ou construtor YAML inseguro;
5. duplicate YAML key;
6. YAML malformado;
7. versão incompatível;
8. estrutura de configuração inválida.

Uma falha produz exatamente uma categoria e uma mensagem pública. Quando mais de uma interpretação parecer possível, prevalece a primeira categoria na ordem acima.

Para versão prevalecer sobre a categoria estrutural residual, o documento já deve ser um mapping e `algorithm_version` deve estar presente como string canônica. Se essa versão for incompatível, ela precede falhas nos demais campos, políticas, `priority_order`, `section_titles` e limites. Ausência ou tipo inválido de `algorithm_version` pertence à categoria de estrutura inválida.

Regras de segurança da mensagem pública:

- deve ser exatamente uma das oito mensagens estáveis;
- não inclui caminho absoluto;
- não inclui conteúdo do arquivo;
- não inclui trecho bruto de YAML;
- não inclui stack trace;
- não inclui nome interno de parser;
- não inclui classe técnica da exceção;
- não inclui detalhes de implementação;
- não inclui dados sensíveis.

Detalhes técnicos ficam acessíveis exclusivamente por `__cause__`. Nenhuma exceção crua de filesystem, Unicode, parser YAML, Pydantic ou validação interna escapa do loader.

## 43. Compatibilidade de versões

No loader público:

```text
config.algorithm_version
== SUPPORTED_PRIORITIZED_BULLETIN_ALGORITHM_VERSION
```

Incompatibilidade no loader é exposta como `PrioritizedBulletinConfigError`, com `str(error) == "unsupported prioritized bulletin configuration version"` e `PrioritizedBulletinVersionError` preservado em `__cause__`.

Em validação programática interna de configuração já materializada, incompatibilidade lança diretamente `PrioritizedBulletinVersionError`.

O resultado copia:

```text
prioritized_bulletin_algorithm_version = config.algorithm_version
prioritized_bulletin_config_version = config.config_version
```

O engine não compara semanticamente versões do Interest Engine; compara apenas strings normalizadas contra o contexto.

## 44. Limites operacionais

Campos:

- `maximum_entries`;
- `maximum_group_members`;
- `maximum_sections`;
- `maximum_items_per_section`.

Regras:

- int estrito;
- bool inválido;
- mínimo `1`;
- exceder limite falha toda a operação;
- sem truncamento;
- sem paginação;
- sem descarte;
- sem boletim parcial.

Ordem:

1. `maximum_entries`, antes da projeção completa;
2. `maximum_group_members`, incrementalmente durante a formação dos grupos, antes de inserir cada novo membro;
3. `maximum_sections`, depois do agrupamento;
4. `maximum_items_per_section`, depois do agrupamento e antes do resultado.

Excesso produz `PrioritizedBulletinLimitError`.

A tentativa de inserir o membro `maximum_group_members + 1` falha antes da inserção. O grupo excedente nunca é materializado por completo e não existe validação desse limite somente depois da formação completa.

## 45. Ordem vinculante de validação

1. estrutura de `PrioritizedBulletinRequest`;
2. estrutura de `PrioritizedBulletinContext`;
3. `maximum_entries`;
4. projeção defensiva dos entries;
5. associação Event–InterestResult;
6. homogeneidade contra context;
7. duplicidade da mesma avaliação;
8. validação estrutural de `pipeline_status` e dos flags de revisão, seguida da consistência de revisão humana;
9. normalização e validação dos campos de Event, datetimes, scores e floats aninhados do InterestResult;
10. inicialização das estruturas vazias de grupos;
11. formação determinística incremental dos grupos; antes de inserir cada novo membro, validação de `maximum_group_members`, falhando na tentativa de inserir o membro `maximum_group_members + 1`, sem materializar o grupo excedente;
12. ordenação dos membros e seleção do representante;
13. formação dos itens;
14. formação das seções;
15. `maximum_sections`;
16. `maximum_items_per_section`;
17. validação dos modelos de saída;
18. retorno.

A primeira etapa que falhar determina o erro público observado.

Dentro da etapa 9, todas as falhas possuem a mesma classe pública `PrioritizedBulletinInputError`. A ordem entre campos dentro dessa etapa e o texto detalhado da mensagem não fazem parte do contrato público; a precedência vinculante é entre as etapas e classes de erro enumeradas.

Request estruturalmente válido acima de `maximum_entries` falha antes da inspeção individual de entries.

- incompatibilidade programática de versão fora do loader.

`PrioritizedBulletinOutputError`:

- violação inesperada de invariantes na construção do modelo público após validações anteriores.

## 47. Precedência entre erros

- estrutura do request precede limites;
- `maximum_entries` precede erros individuais;
- associação precede contexto;
- contexto precede duplicidade;
- duplicidade precede revisão;
- revisão precede datetime;
- datetime precede formação dos grupos;
- `maximum_group_members` ocorre incrementalmente durante a formação do grupo, antes de cada inserção; a tentativa de inserir o membro excedente falha sem materializar o grupo completo;
- erros de seções ocorrem depois da formação dos itens;
- configuração inválida impede a construção do engine e precede qualquer erro de request;
- erro de output ocorre somente depois de todas as validações anteriores.

No fluxo de `PrioritizedBulletinEngine.build()`, cada erro específico é lançado diretamente.

No fluxo de `build()`, nenhum erro específico é convertido em `PrioritizedBulletinInputError`.

Exceção normativa exclusiva do loader público: `PrioritizedBulletinVersionError` é capturado e encapsulado por `PrioritizedBulletinConfigError`, com `__cause__` igual à instância de `PrioritizedBulletinVersionError`. Fora do loader público, incompatibilidade programática de versão lança diretamente `PrioritizedBulletinVersionError`.

Construção pública dos modelos:

## 49. Modelo de saída e invariantes

Antes do retorno, validar:

- modelo estrito e frozen;
- contexto estruturalmente igual por valor a `request.context`;
- versões exatamente iguais por valor às strings da configuração;
- contadores corretos;
- seções sem duplicidade de identidade;
- seções em ordem configurada;
- itens em ordem total;
- IDs de membros únicos;
- membros e IDs na mesma ordem;
- nenhum candidato validado do grupo omitido de `members` ou `member_event_ids`;
- scores, níveis, matches, reasons e review de cada membro iguais aos do candidato validado correspondente;
- representante na primeira posição;
- scores de primeiro nível iguais aos do representante;
- reasons e matches de primeiro nível iguais aos do representante;
- conteúdo textual igual ao snapshot do representante depois da normalização definida na seção 20;
- datetimes iguais ao snapshot do representante depois da normalização UTC definida na seção 21;
- revisão do item igual ao OR dos membros;
- chave de ordenação do item construída exclusivamente com os valores do representante;
- `item.requires_human_review` agregado ausente da chave de ordenação;
- cada item presente em uma única seção;
- `total_groups == total_items`.

Falha inesperada produz `PrioritizedBulletinOutputError`, preservando a causa.

```python
canonical_context.traps[Clamped] = False
canonical_context.traps[DivisionByZero] = True
canonical_context.traps[FloatOperation] = True
canonical_context.traps[Inexact] = False
canonical_context.traps[InvalidOperation] = True
canonical_context.traps[Overflow] = True
canonical_context.traps[Rounded] = False
canonical_context.traps[Subnormal] = False
canonical_context.traps[Underflow] = True

canonical_decimal = Decimal(str(value)).quantize(
    Decimal("0.000001"),
    rounding=ROUND_HALF_EVEN,
    context=canonical_context,
)

if canonical_decimal == 0:
    canonical_decimal = Decimal("0.000000")

canonical_text = format(canonical_decimal, ".6f")
```

Um novo `Context` dedicado com esses valores literais é criado dentro de cada chamada de `serialize_prioritized_bulletin()`. Todas as conversões de float dessa chamada usam essa instância exclusiva. Uma chamada posterior ou concorrente cria outra instância.

O Context não é obtido por `getcontext()`, `localcontext()` ou cópia de qualquer contexto global. Ele não é armazenado em variável global mutável, singleton, cache ou estado de módulo. Mutação acidental ou deliberada da instância pertencente a uma chamada não pode afetar nenhuma outra chamada.

A instrumentação dos testes observa a criação do Context por monkeypatch, spy ou factory package-private, sem expor o `Context` na API pública.

Comportamento vinculante dos sinais:

- `Inexact=False` e `Rounded=False`, porque a quantização para seis casas é intencional;
- `InvalidOperation=True`, `Overflow=True`, `Underflow=True` e `DivisionByZero=True`, para converter qualquer ocorrência inesperada em falha explícita;
- `FloatOperation=True`, porque a fronteira normativa é `Decimal(str(value))`, nunca construção direta a partir de float;
- `Clamped=False` e `Subnormal=False`; os limites fixos de expoente continuam independentes do processo.

Qualquer `DecimalException` inesperada durante a serialização de modelo público já construído, incluindo `InvalidOperation`, `Overflow`, `Underflow` ou `DivisionByZero`, produz `PrioritizedBulletinOutputError`, preservando a exceção original em `__cause__`.

Exemplos:

```text
0.0    → "0.000000"
-0.0   → "0.000000"
1.0    → "1.000000"
0.125  → "0.125000"
```

Não existe notação científica.

Não existem números JSON para esses campos na identidade canônica.

Essa transformação:

- ocorre somente durante serialização;
- não altera o modelo;
- não altera ordenação;
- não altera representante;
- não altera níveis;
- não recalcula interesse.

## 53. Determinismo

Execuções repetidas com o mesmo request validado e a mesma configuração validada produzem resultados estruturalmente iguais por valor.

Para essa regra, “mesmo request” significa o mesmo conteúdo estrutural em todos os campos observados. Mutação do `Event` upstream ou de qualquer valor de entrada entre chamadas constitui um request semanticamente diferente e não participa da garantia de igualdade entre execuções repetidas. A mutabilidade posterior ao retorno continua sem alterar o boletim já construído, conforme a seção 12.

Igualdade estrutural significa comparação pelo conteúdo integral dos modelos públicos:

```python
resultado_a == resultado_b
```

Não é exigida identidade de instância Python e não deve ser usado como critério:

```python
resultado_a is resultado_b
```

Cada chamada de `build()` constrói seu resultado independentemente, sem cache, singleton, memoização global, estado global mutável ou reutilização de instância. O contrato avalia os resultados somente por igualdade estrutural e nunca por identidade Python.

Resultados estruturalmente iguais possuem:

- mesmo contexto;
- mesmos grupos;
- mesmos membros;
- mesma ordem dos membros;
- mesmo representante;
- mesmos itens;
- mesma ordem dos itens;
- mesmas seções;
- mesma ordem das seções;
- todos os campos públicos iguais por valor;
- string canônica exatamente igual, com representação UTF-8 byte a byte idêntica.

A mesma definição de chave total é aplicada deterministicamente aos candidatos, à escolha do representante e aos itens. Para itens, o registro representativo é o representante; o OR público de review não altera essa chave.

Permutações semanticamente equivalentes de `request.entries` produzem resultados estruturalmente iguais por valor e strings canônicas exatamente iguais byte a byte.

O componente não depende de:

- ordem de dicionários de entrada;
- relógio;
- locale;
- timezone local;
- hash aleatório;
- estado global;
- I/O;
- cache, singleton, memoização global ou reutilização de instância como mecanismo de determinismo;
- ordem acidental de set ou mapping.

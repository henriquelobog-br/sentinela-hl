# Documento 112.7E — Event Radar Implementation

## Engineering Brief para implementação determinística do Event Radar

**Status:** Draft
**Versão:** 1.0
**Epic:** Scientific Intelligence

**Complementa, sem substituir:**

- Documento 112.7C — Event Radar

**Dependências:**

- ADR-007 — Scientific Prioritization Architecture
- Documento 112.7A — Scientific Taxonomy
- Documento 112.7C — Event Radar
- Documento 112.7D — Concept Fingerprint
- contrato `Event` existente em `sentinela.core.models`
- contrato `ConceptFingerprint` definido pelo Documento 112.7D

O `ResearchProfile` não é entrada nem dependência técnica deste componente.

---

# 1. Objetivo

Este documento define o contrato de engenharia necessário para implementar o Event Radar especificado funcionalmente no Documento 112.7C.

O Event Radar responde exclusivamente:

> **Qual é a significância científica objetiva deste evento, independentemente de qualquer agenda de pesquisa?**

Ele recebe um `Event` validado e seu `ConceptFingerprint`, identifica sinais científicos configurados, calcula um score determinístico e produz um `EventRadarResult` explicável e imutável.

Este documento não implementa o componente.

---

# 2. Relação com o Documento 112.7C

O Documento 112.7C permanece como especificação funcional do Event Radar.

O presente Engineering Brief preserva os requisitos funcionais já definidos:

- medir importância científica própria;
- produzir score entre `0.0` e `1.0`;
- classificar o resultado como `LOW`, `MODERATE`, `HIGH` ou `CRITICAL`;
- produzir sinais encontrados e razões explicáveis;
- ser independente do Research Profile;
- usar apenas conceitos canônicos da Scientific Taxonomy;
- não usar LLM;
- não usar embeddings;
- não usar banco;
- não usar inferência probabilística;
- produzir o mesmo resultado para a mesma entrada.

Este documento acrescenta somente os detalhes executáveis necessários para implementação:

- entrada pública exata;
- modelos Pydantic;
- enum e thresholds;
- catálogo versionado de sinais;
- regras de ativação;
- algoritmo do score;
- ordenação;
- configuração;
- API pública;
- erros;
- testes e critérios de aceite.

Em caso de dúvida sobre objetivo ou responsabilidade funcional, o Documento 112.7C continua sendo a referência funcional. Este documento governa o contrato técnico da implementação.

---

# 3. Motivação de engenharia

O Documento 112.7C define o que o Radar deve responder, mas uma implementação reproduzível também precisa definir:

- quais dados entram no componente;
- como conceitos canônicos ativam sinais;
- como cada sinal contribui para o score;
- como o score produz um nível;
- como razões são geradas e ordenadas;
- como configuração e catálogo são versionados;
- como entradas incompatíveis falham;
- como provar ausência de I/O, rede e inferência oculta.

Sem esses contratos, implementações diferentes poderiam satisfazer a intenção funcional e ainda produzir resultados incompatíveis.

# 4. Posição na arquitetura

```text
Event validado
        +
Scientific Taxonomy
        │
        ▼
Concept Fingerprint
        │
        ├──────────────┐
        │              │
        ▼              ▼
ConceptFingerprint   Event
        │              │
        └──────┬───────┘
               ▼
          Event Radar
               │
               ▼
       EventRadarResult
               │
               ▼
         Interest Engine
```

A resolução taxonômica acontece antes do Event Radar, dentro do Concept Fingerprint.

O Radar:

- não recebe `TaxonomyIndex` em runtime;
- não reexamina título, resumo, keywords ou texto livre;
- não resolve nomes ou sinônimos;
- não expande relações taxonômicas;
- trabalha exclusivamente com IDs canônicos presentes no fingerprint.

O Documento 112.7D é o próximo componente da trilha de implementação. Este documento prepara a implementação posterior do Radar.

---

# 5. Responsabilidade única

O Event Radar deve:

- receber `Event` e `ConceptFingerprint`;
- validar identidade e compatibilidade entre as entradas;
- carregar uma configuração já validada;
- identificar sinais ativados por conceitos elegíveis do fingerprint;
- selecionar o maior peso de conceito compatível para cada sinal;
- calcular uma contribuição por sinal distinto;
- somar e limitar as contribuições em `1.0`;
- arredondar o score final para seis casas decimais;
- derivar o nível segundo thresholds explícitos;
- produzir IDs de sinais ordenados;
- produzir razões determinísticas em português;
- retornar `EventRadarResult` imutável.

O Event Radar não deve:

- calcular interesse pessoal;
- consumir `ResearchProfile`;
- fazer matching textual;
- consultar `TaxonomyIndex`;
- resolver sinônimos;
- usar keywords do `Event`;
- inferir conceitos relacionados;
- alterar o `Event`;
- alterar o `ConceptFingerprint`;
- consultar banco;
- persistir resultados;
- acessar rede;
- chamar LLM;
- gerar ou consultar embeddings;
- usar banco vetorial;
- aplicar aprendizado de máquina;
- criar bônus, penalidades ou interações ocultas.

# 6. Terminologia

## 6.1 Significância científica

Importância objetiva atribuída ao evento pelos sinais científicos configurados, independentemente de qualquer pesquisador.

## 6.2 Interesse científico

Relevância de um evento para uma agenda de pesquisa específica. Pertence ao Interest Engine, não ao Event Radar.

## 6.3 Sinal científico

Regra configurada e versionada que associa um ID estável a um conjunto de conceitos canônicos e a um peso explícito.

## 6.4 Conceito elegível

Conceito presente no `ConceptFingerprint` como correspondência direta ou ancestral canônico explicitamente materializado pelo fingerprint.

Um conceito presente exclusivamente por expansão `related` não é elegível para ativar sinal na V1.

## 6.5 Contribuição

Produto entre o peso configurado do sinal e o maior peso de conceito elegível correspondente.

## 6.6 Razão

String determinística em português que explica qual sinal foi ativado, por qual conceito e com quais valores numéricos.

---

# 7. Requisitos vinculantes

1. A entrada pública é `Event + ConceptFingerprint`.
2. O Radar não recebe `TaxonomyIndex`.
3. O Radar não recebe nem consome `ResearchProfile`.
4. A saída é `EventRadarResult`.
5. O score permanece entre `0.0` e `1.0`.
6. Os níveis são `LOW`, `MODERATE`, `HIGH` e `CRITICAL`.
7. Os thresholds são fixos para o algoritmo V1 e declarados na configuração.
8. Sinais possuem IDs estáveis, nunca nomes livres como identidade.
9. Somente conceitos elegíveis do fingerprint ativam sinais.
10. Cada sinal contribui no máximo uma vez.
11. O maior peso de conceito compatível governa a contribuição do sinal.
12. O score é a soma limitada a `1.0` e arredondada para seis casas decimais.
13. Nenhum campo semântico do `Event` participa do score na V1.
14. Event e fingerprint precisam representar o mesmo evento.
15. Incompatibilidades falham sem correção automática.
16. Razões são determinísticas e não usam LLM.
17. Configuração e catálogo são validados por Pydantic.
18. `evaluate()` é síncrono, puro e sem I/O.
19. O resultado não contém timestamp dinâmico nem `event_id`.
20. A mesma entrada e a mesma configuração produzem exatamente a mesma saída.
21. `RadarSignal.domain` aceita somente os oito valores de `RadarDomain`.
22. `EventRadarLimits` é obrigatório e imutável.
23. Não existem limites ocultos no engine.
24. `algorithm_version` deve ser exatamente `SUPPORTED_ALGORITHM_VERSION = "1.0"`.
25. Versão de algoritmo incompatível produz `EventRadarVersionError` sem fallback.

# 8. Entrada

A API pública recebe exatamente:

```python
evaluate(
    event: Event,
    fingerprint: ConceptFingerprint,
) -> EventRadarResult
```

## 8.1 Event

O engine reutiliza o contrato real `sentinela.core.models.Event`.

Na V1, o `Event` serve somente para:

- validação estrutural;
- obtenção do identificador do evento;
- comparação de identidade com o fingerprint.

Nenhum destes campos participa do score:

```text
epistemic_status
confidence_score
category
country
scientific_area
entities
keywords
evidence
occurred_at
pipeline_status
requires_human_review
review_decision
validated_by
validated_at
title
summary
```

O Radar não usa texto ou metadados do `Event` para compensar conceitos ausentes no fingerprint.

## 8.2 ConceptFingerprint

O Radar consome o contrato `ConceptFingerprint` definido pelo Documento 112.7D.

Os dados relevantes são:

- `event_id`;
- `taxonomy_version`;
- `algorithm_version`;
- coleção ordenada de `ConceptSignal`;
- `concept_id`;
- `domain_id`;
- `weight`;
- `direct_weight`;
- `inherited_weight`;
- `related_weight`;
- evidências de proveniência conceitual;
- versão e hash quando presentes no contrato aprovado do fingerprint.

## 8.3 Conceitos elegíveis

Um `ConceptSignal` é elegível quando:

```text
direct_weight > 0
ou
inherited_weight > 0
```

Um conceito com apenas:

```text
related_weight > 0
```

não ativa sinais na V1.

Para um conceito elegível, `concept_weight` é o campo final `weight` publicado pelo `ConceptSignal`.

## 8.4 Consistência entre entradas

Antes de calcular qualquer sinal, o engine deve validar:

- `event.id` existe;
- `fingerprint.event_id` existe;
- `event.id == fingerprint.event_id`;
- o fingerprint foi construído e validado pelo contrato Pydantic aprovado;
- a versão da Taxonomia do fingerprint é compatível com a configuração do Radar;
- os campos e pesos usados pelo Radar respeitam seus limites contratuais.

O Radar não adiciona um campo `validated` ao fingerprint.

Neste contrato, fingerprint validado significa:

- instância aceita pelo modelo Pydantic do Documento 112.7D;
- invariantes estruturais satisfeitos;
- versões obrigatórias presentes;
- conceitos e pesos necessários legíveis pelo Radar.

Qualquer falha interrompe a avaliação antes do score.

# 9. Saída

```python
class EventRadarResult(BaseModel):
    model_config = ConfigDict(
        frozen=True,
        extra="forbid",
    )

    significance_score: float = Field(ge=0.0, le=1.0)
    significance_level: EventSignificance
    matched_signals: tuple[str, ...]
    reasons: tuple[str, ...]
```

Regras:

- `significance_score` entre `0.0` e `1.0`;
- score arredondado para seis casas decimais;
- `matched_signals` imutável;
- `reasons` imutável;
- campos extras proibidos;
- nenhum timestamp;
- nenhum `event_id`;
- nenhuma referência mutável à entrada;
- serialização estável para a mesma entrada e configuração.

## 9.1 Ordenação de matched_signals

`matched_signals` contém cada ID ativado uma única vez.

A ordenação é lexicográfica crescente pelo ID do sinal.

Exemplo:

```text
atmosphere.mineral_dust
remote_sensing.satellite_observation
```

## 9.2 Ordenação de reasons

As razões são ordenadas por:

1. contribuição decrescente;
2. ID do sinal em ordem lexicográfica crescente.

A ordem de `reasons` não precisa acompanhar a ordem lexicográfica de `matched_signals`.

---

# 10. EventSignificance

```python
from enum import StrEnum


class EventSignificance(StrEnum):
    LOW = "low"
    MODERATE = "moderate"
    HIGH = "high"
    CRITICAL = "critical"
```

O enum não reutiliza:

```text
PASS
ESCALATE
REJECT
```

Esses estados pertencem ao Agente 113.

---

# 11. Thresholds

O algoritmo V1 utiliza:

```text
0.00 <= score < 0.25  → LOW
0.25 <= score < 0.50  → MODERATE
0.50 <= score < 0.75  → HIGH
0.75 <= score <= 1.00 → CRITICAL
```

Todos os limites inferiores são inclusivos.

Casos de fronteira obrigatórios:

```text
0.000000 → LOW
0.249999 → LOW
0.250000 → MODERATE
0.499999 → MODERATE
0.500000 → HIGH
0.749999 → HIGH
0.750000 → CRITICAL
1.000000 → CRITICAL
```

Os thresholds aparecem na configuração para auditabilidade, mas a configuração V1 deve validar exatamente esses valores.

Alterar thresholds exige nova versão de algoritmo e nova aprovação arquitetural.

---

# 12. Catálogo de sinais V1

O catálogo é configurável, versionado e validado.

Domínios autorizados:

```text
atmosphere             → atmosfera
astronomy              → astronomia
oceanography           → oceanografia
geology                → geologia
volcanology            → vulcanologia
seismology             → sismologia
scientific_geopolitics → geopolítica científica
remote_sensing         → sensoriamento remoto
```

Os identificadores à esquerda são os únicos valores canônicos aceitos na V1.

Cada sinal declara:

```text
id
domain
description
concept_ids
weight
reason_template
enabled
```

Modelo previsto:

```python
class RadarDomain(StrEnum):
    ATMOSPHERE = "atmosphere"
    ASTRONOMY = "astronomy"
    OCEANOGRAPHY = "oceanography"
    GEOLOGY = "geology"
    VOLCANOLOGY = "volcanology"
    SEISMOLOGY = "seismology"
    SCIENTIFIC_GEOPOLITICS = "scientific_geopolitics"
    REMOTE_SENSING = "remote_sensing"


class RadarSignal(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    id: str
    domain: RadarDomain
    description: str
    concept_ids: tuple[str, ...]
    weight: float = Field(ge=0.0, le=1.0)
    reason_template: str
    enabled: bool = True
```

Regras:

- `id` é estável e único no catálogo;
- `id` usa namespace de domínio, por exemplo `atmosphere.mineral_dust`;
- `domain` usa obrigatoriamente um valor de `RadarDomain`;
- `concept_ids` contém IDs canônicos esperados no fingerprint;
- `concept_ids` não contém nomes, sinônimos ou texto livre;
- `concept_ids` não contém duplicatas;
- `weight` está entre `0.0` e `1.0`;
- `reason_template` é não vazio e usa apenas placeholders permitidos;
- sinal desabilitado nunca ativa nem contribui;
- a ordenação original do YAML não altera o resultado.

O conteúdo científico e os pesos do catálogo produtivo devem ser explicitamente curados. Exemplos deste documento não constituem automaticamente o catálogo produtivo.

---

# 13. Identificação de sinais

Para cada sinal habilitado:

1. obter os `concept_ids` configurados;
2. localizar no fingerprint somente conceitos elegíveis;
3. ignorar conceitos presentes exclusivamente por `related_weight`;
4. selecionar o conceito compatível com maior `ConceptSignal.weight`;
5. em empate de peso, selecionar o menor `concept_id` em ordem lexicográfica;
6. ativar o sinal uma única vez;
7. calcular uma única contribuição;
8. preservar os valores usados para gerar a razão.

É proibido durante a identificação:

- ler título ou resumo;
- ler keywords;
- usar `scientific_area` ou `category`;
- resolver sinônimos;
- executar matching semântico;
- consultar a Taxonomia;
- expandir `parent`;
- expandir `related`;
- inferir conceito ausente;
- consultar qualquer fonte externa.

## 13.1 Sinais duplicados

Um sinal contribui no máximo uma vez, mesmo quando:

- vários `concept_ids` do sinal estão presentes;
- o mesmo conceito aparece em múltiplas evidências;
- o fingerprint registra múltiplas origens para o conceito;
- conceitos diretos e ancestrais ativam o mesmo sinal.

## 13.2 Sinais distintos

Sinais com IDs diferentes contribuem independentemente, mesmo quando compartilham um conceito.

Não existe deduplicação entre sinais distintos na V1.

---

# 14. Algoritmo do score

Para cada sinal distinto ativado:

```text
contribution = signal_weight × concept_weight
```

Onde:

- `signal_weight` é o peso explícito do catálogo;
- `concept_weight` é o maior `ConceptSignal.weight` elegível entre os conceitos configurados para o sinal.

Score bruto:

```text
raw_score = soma das contribuições dos sinais distintos
```

Score limitado:

```text
bounded_score = min(1.0, raw_score)
```

Score final:

```text
significance_score = round(bounded_score, 6)
```

Regras vinculantes:

- cada contribuição permanece entre `0.0` e `1.0`;
- cada sinal contribui uma vez;
- conceitos duplicados não duplicam contribuição;
- sinais distintos contribuem independentemente;
- nenhuma interação entre sinais;
- nenhum bônus;
- nenhuma penalidade;
- nenhum multiplicador oculto;
- nenhuma dependência do Research Profile;
- nenhuma dependência dos campos semânticos do Event;
- ausência de sinais produz `0.0`;
- saturação ocorre em `1.0`;
- arredondamento ocorre somente depois da saturação.

## 14.1 Independência da ordem

O score não depende da ordem:

- dos sinais no YAML;
- dos conceitos no fingerprint;
- dos `concept_ids` dentro de um sinal;
- das evidências dentro de `ConceptSignal`.

---

# 15. Explicabilidade

Cada sinal ativado produz exatamente uma razão.

A razão deve informar:

- ID do sinal;
- conceito responsável;
- peso do sinal;
- peso do conceito;
- contribuição.

Placeholders permitidos em `reason_template`:

```text
signal_id
concept_id
signal_weight
concept_weight
contribution
```

Valores numéricos nas razões devem usar seis casas decimais.

Exemplo de template:

```text
Sinal {signal_id} ativado pelo conceito {concept_id}: peso do sinal {signal_weight}, peso do conceito {concept_weight}, contribuição {contribution}.
```

O template é parte da configuração versionada.

Templates não podem:

- chamar código arbitrário;
- acessar atributos não permitidos;
- depender de locale do sistema;
- depender de LLM;
- inserir dados textuais do Event;
- omitir os cinco elementos obrigatórios.

---

# 16. Determinismo e reprodutibilidade

A mesma combinação de:

```text
Event
ConceptFingerprint
EventRadarConfig
```

deve produzir `EventRadarResult` logicamente e serialmente idêntico.

O resultado não possui:

- timestamp;
- UUID gerado durante avaliação;
- ordem derivada de `set` sem ordenação;
- texto gerado dinamicamente;
- dependência de relógio;
- dependência de rede;
- dependência de banco;
- aleatoriedade.

Toda coleção deve ser ordenada explicitamente antes da criação do resultado.

---

# 17. Versionamento

O Radar depende de três versões explícitas:

```text
config_version
algorithm_version
compatible_taxonomy_version
```

## 17.1 config_version

Identifica o conteúdo completo de `config/event_radar.yaml`, incluindo catálogo, pesos, templates e thresholds.

## 17.2 Algorithm version

Identifica as regras de ativação, contribuição, saturação, arredondamento, ordenação e classificação.

Contrato da V1:

```python
SUPPORTED_ALGORITHM_VERSION = "1.0"
```

Na construção de `EventRadar`, `config.algorithm_version` deve ser comparado com `SUPPORTED_ALGORITHM_VERSION`.

Qualquer valor diferente deve produzir `EventRadarVersionError`.

O componente não:

- realiza fallback;
- seleciona automaticamente outra versão;
- aceita compatibilidade implícita;
- tenta executar uma configuração de algoritmo desconhecida.

Qualquer alteração nas regras do algoritmo exige nova versão e aprovação arquitetural.

## 17.3 Compatible taxonomy version

Declara a versão de Taxonomia compatível com os `concept_ids` usados pelo catálogo.

Ela deve ser igual a `fingerprint.taxonomy_version`.

Incompatibilidade falha com `EventRadarVersionError`.

O `EventRadarResult` não repete essas versões. A configuração usada deve permanecer rastreável pelo chamador e pelo artefato versionado em Git.

---

# 18. Configuração

Arquivo previsto:

```text
config/event_radar.yaml
```

O arquivo deve conter:

- `config_version`;
- `algorithm_version`;
- `compatible_taxonomy_version`;
- thresholds;
- limites;
- catálogo de sinais;
- pesos dos sinais;
- templates de razões.

Modelos previstos:

```python
class EventRadarThresholds(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    moderate_min: float = Field(default=0.25, ge=0.0, le=1.0)
    high_min: float = Field(default=0.50, ge=0.0, le=1.0)
    critical_min: float = Field(default=0.75, ge=0.0, le=1.0)


class EventRadarLimits(BaseModel):
    model_config = ConfigDict(
        frozen=True,
        extra="forbid",
    )

    maximum_signals: int
    maximum_concepts_per_signal: int
    maximum_signal_id_length: int
    maximum_description_length: int
    maximum_reason_template_length: int


class EventRadarConfig(BaseModel):
    model_config = ConfigDict(
        frozen=True,
        extra="forbid",
    )

    config_version: str
    algorithm_version: str
    compatible_taxonomy_version: str
    thresholds: EventRadarThresholds
    limits: EventRadarLimits
    signals: tuple[RadarSignal, ...]
```

`EventRadarThresholds` deve validar conjuntamente:

- todos os valores entre `0.0` e `1.0`;
- ordem estritamente crescente;
- `moderate_min == 0.25` na V1;
- `high_min == 0.50` na V1;
- `critical_min == 0.75` na V1;
- cobertura completa de `[0.0, 1.0]` quando combinada com o limite inferior implícito de `LOW`, igual a `0.0`;
- ausência de lacunas;
- ausência de sobreposição;
- limite superior de `CRITICAL` igual a `1.0`, garantido pelo limite de `significance_score`.

Validações obrigatórias:

- strings de versão não vazias;
- `algorithm_version == SUPPORTED_ALGORITHM_VERSION`;
- thresholds exatamente iguais aos valores aprovados para V1;
- IDs de sinais únicos;
- IDs de sinais estáveis e namespaced;
- domínios representados exclusivamente por `RadarDomain`;
- `concept_ids` canônicos e não vazios;
- ausência de duplicatas em `concept_ids`;
- pesos entre `0.0` e `1.0`;
- templates válidos;
- placeholders obrigatórios presentes;
- nenhum campo extra;
- pelo menos um sinal configurado;
- limites obrigatórios e positivos;
- quantidade de sinais dentro de `maximum_signals`;
- quantidade de conceitos por sinal dentro de `maximum_concepts_per_signal`;
- comprimentos dentro dos limites configurados;
- configuração imutável depois do carregamento.

O engine não deve conter pesos, thresholds, sinais, templates ou limites como constantes mágicas.

Não existem defaults ocultos de limites no engine.

# 23. API pública

Classe pública:

```python
class EventRadar:
    def __init__(self, config: EventRadarConfig) -> None:
        ...

    def evaluate(
        self,
        event: Event,
        fingerprint: ConceptFingerprint,
    ) -> EventRadarResult:
        ...
```

Construção:

```python
config = load_event_radar_config("config/event_radar.yaml")
radar = EventRadar(config)
```

Durante a construção, `EventRadar` deve:

- comparar `config.algorithm_version` com `SUPPORTED_ALGORITHM_VERSION`;
- produzir `EventRadarVersionError` quando os valores forem diferentes;
- validar os limites antes de preparar os índices internos;
- rejeitar configuração que exceda qualquer limite;
- preservar `config.limits` imutável durante todas as chamadas a `evaluate()`.

Uso:

```python
result = radar.evaluate(
    event=event,
    fingerprint=fingerprint,
)
```

`evaluate()` deve ser:

- síncrono;
- puro;
- sem I/O;
- sem efeitos colaterais;
- seguro para chamadas repetidas;
- independente de ordem acidental das coleções de entrada.

O carregamento do YAML acontece fora de `evaluate()`.

# 25. Exemplo completo

Os valores de catálogo deste exemplo são fixtures ilustrativas, não pesos produtivos aprovados.

Entrada conceitual:

```python
event = Event(
    id=event_id,
    title="Mineral dust plume observed by satellite",
    summary="Validated scientific event.",
    epistemic_status=EpistemicStatus.CONFIRMED_FACT,
    confidence_score=0.90,
)

fingerprint = ConceptFingerprint(
    event_id=event_id,
    taxonomy_version="1",
    algorithm_version="1",
    concepts=(
        ConceptSignal(
            concept_id="mineral_dust",
            domain_id="atmospheric_science",
            weight=0.80,
            direct_weight=0.80,
            inherited_weight=0.00,
            related_weight=0.00,
            evidence=(...),
        ),
        ConceptSignal(
            concept_id="satellite_instruments",
            domain_id="remote_sensing",
            weight=0.50,
            direct_weight=0.50,
            inherited_weight=0.00,
            related_weight=0.00,
            evidence=(...),
        ),
    ),
    unmatched_terms=(),
    source_fields=("title",),
)
```

Configuração de fixture:

```text
atmosphere.mineral_dust
signal_weight = 0.60
concept_weight = 0.80
contribution = 0.48

remote_sensing.satellite_observation
signal_weight = 0.40
concept_weight = 0.50
contribution = 0.20
```

Cálculo:

```text
raw_score = 0.48 + 0.20
raw_score = 0.68

bounded_score = min(1.0, 0.68)
bounded_score = 0.68

significance_score = 0.680000
significance_level = HIGH
```

Saída:

```python
EventRadarResult(
    significance_score=0.68,
    significance_level=EventSignificance.HIGH,
    matched_signals=(
        "atmosphere.mineral_dust",
        "remote_sensing.satellite_observation",
    ),
    reasons=(
        (
            "Sinal atmosphere.mineral_dust ativado pelo conceito "
            "mineral_dust: peso do sinal 0.600000, peso do conceito "
            "0.800000, contribuição 0.480000."
        ),
        (
            "Sinal remote_sensing.satellite_observation ativado pelo "
            "conceito satellite_instruments: peso do sinal 0.400000, "
            "peso do conceito 0.500000, contribuição 0.200000."
        ),
    ),
)
```

Alterar `confidence_score`, título ou resumo sem alterar a identidade e o fingerprint não muda o resultado na V1.

# 26. Relação com a Scientific Taxonomy

A Scientific Taxonomy continua sendo a fonte de verdade dos conceitos canônicos.

O Radar não recebe a Taxonomia nem `TaxonomyIndex`.

Ele assume que:

- a resolução de nomes e sinônimos já ocorreu;
- os conceitos do fingerprint são canônicos;
- a versão da Taxonomia foi registrada no fingerprint;
- o catálogo foi curado para uma versão compatível da Taxonomia.

O Radar não corrige conceito desconhecido e não procura substituto.

---

# 27. Relação com o Concept Fingerprint

O Concept Fingerprint responde:

> Quais conceitos científicos estão representados neste evento e com qual força?

O Event Radar responde:

> Quais sinais científicos esses conceitos ativam e qual significância objetiva resulta deles?

O Radar depende do fingerprint para:

- identidade do evento;
- IDs canônicos;
- pesos conceituais;
- distinção entre presença direta, ancestral e relacionada;
- versão da Taxonomia;
- proveniência auditável anterior.

O Radar não modifica, completa ou recalcula o fingerprint.

---

# 28. Relação com o Research Profile

Nenhuma dependência técnica.

O Radar:

- não recebe `ResearchProfile`;
- não conhece pesquisador;
- não consulta prioridades;
- não usa exclusões;
- não usa regiões de interesse;
- não usa instrumentos preferidos;
- não calcula relevância pessoal.

O Research Profile será consumido pelo Interest Engine.

# 29. Relação com o Interest Engine

O Interest Engine é o consumidor posterior do resultado.

Fluxo previsto:

```text
ConceptFingerprint
        +
EventRadarResult
        +
ResearchProfile
        │
        ▼
Interest Engine
```

O Interest Engine não deve precisar reinterpretar `reasons` para recuperar o score. O contrato estruturado fornece diretamente:

- `significance_score`;
- `significance_level`;
- IDs estáveis em `matched_signals`;
- razões auditáveis.

# 30. Relação com o Agente 113

O Agente 113 avalia sustentação científica, proveniência, rótulo epistêmico e calibração.

O Event Radar opera depois da validação e não reutiliza as decisões:

```text
pass
escalate
reject
```

O Radar não altera classificações, decisões ou estado do pipeline.

# 32. Erros públicos

Erros previstos:

```python
class EventRadarError(Exception):
    pass


class EventRadarConfigError(EventRadarError):
    pass


class EventRadarInputError(EventRadarError):
    pass


class EventFingerprintMismatchError(EventRadarInputError):
    pass


class EventRadarVersionError(EventRadarInputError):
    pass
```

## 32.1 EventRadarConfigError

Usado para:

- YAML inválido;
- configuração ausente;
- campo extra;
- sinal duplicado;
- domínio não autorizado;
- peso inválido;
- threshold diferente do aprovado para V1;
- template inválido;
- `concept_ids` vazio ou duplicado;
- quantidade de sinais acima de `maximum_signals`;
- quantidade de conceitos acima de `maximum_concepts_per_signal`;
- ID acima de `maximum_signal_id_length`;
- descrição acima de `maximum_description_length`;
- template acima de `maximum_reason_template_length`.

## 32.2 EventRadarInputError

Usado para entrada estrutural inválida que não seja mismatch específico ou versão incompatível.

## 32.3 EventFingerprintMismatchError

Usado quando:

- `event.id` está ausente;
- `fingerprint.event_id` está ausente;
- os identificadores são diferentes.

## 32.4 EventRadarVersionError

Usado quando:

- `fingerprint.taxonomy_version` está ausente;
- a versão é incompatível com `compatible_taxonomy_version`;
- versões obrigatórias do fingerprint estão ausentes ou inválidas;
- `config.algorithm_version != SUPPORTED_ALGORITHM_VERSION`.

Nenhum erro permite fallback silencioso.

O Radar não tenta:

- corrigir IDs;
- atualizar versão;
- remover conceito inválido;
- desabilitar sinal inválido;
- usar configuração parcial;
- retornar score aproximado.

# 33. Performance

O custo de uma avaliação deve ser proporcional a:

- número de sinais habilitados;
- quantidade de `concept_ids` por sinal;
- quantidade de conceitos no fingerprint.

A construção do `EventRadar` deve preparar índices imutáveis para evitar varreduras desnecessárias.

Evitar durante `evaluate()`:

- releitura do YAML;
- reconstrução completa do catálogo;
- compilação repetida de validadores;
- acesso ao filesystem;
- normalização textual;
- consulta à Taxonomia;
- cópia profunda desnecessária das entradas.

Não há meta rígida bloqueante de latência na V1.

---

# 34. Segurança e limites

A configuração deve possuir limites explícitos e validados para impedir catálogo acidentalmente inválido ou excessivo.

Os limites obrigatórios da V1 são serializados em `config/event_radar.yaml` e representados por `EventRadarLimits`:

```yaml
limits:
  maximum_signals: 256
  maximum_concepts_per_signal: 64
  maximum_signal_id_length: 128
  maximum_description_length: 1024
  maximum_reason_template_length: 2048
```

Regras:

- não existem defaults ocultos no engine;
- os limites são obrigatórios;
- os limites são versionados por `config_version`;
- os limites são validados antes da construção do engine;
- os limites permanecem imutáveis durante `evaluate()`;
- a quantidade de sinais não pode exceder `maximum_signals`;
- `concept_ids` de cada sinal não pode exceder `maximum_concepts_per_signal`;
- o comprimento do ID não pode exceder `maximum_signal_id_length`;
- o comprimento da descrição não pode exceder `maximum_description_length`;
- o comprimento do template não pode exceder `maximum_reason_template_length`.

Falhas de limite são `EventRadarConfigError`.

Nenhum truncamento silencioso é permitido.

# 42. Riscos

## 42.1 Catálogo excessivamente amplo

Sinais com muitos conceitos podem ativar eventos pouco específicos.

Mitigação contratual:

- catálogo versionado;
- limites obrigatórios validados;
- IDs auditáveis;
- conceitos explícitos por sinal;
- fixtures científicas;
- revisão humana da configuração.

## 42.2 Pesos arbitrários

Pesos de sinais representam decisões explícitas de configuração.

Mitigação contratual:

- nenhum peso oculto;
- peso visível no YAML;
- `config_version`;
- contribuição exposta na razão;
- mudança de peso rastreável em Git.

## 42.3 Thresholds não calibrados empiricamente

Os thresholds V1 são vinculantes, mas ainda podem precisar de avaliação futura com dados reais.

Mitigação contratual:

- fronteiras explícitas;
- testes completos;
- benchmark e fixtures;
- qualquer alteração exige nova versão e aprovação.

## 42.4 Dupla contagem

Múltiplos conceitos podem ativar o mesmo sinal.

Mitigação contratual:

- uma contribuição por ID de sinal;
- maior peso compatível;
- testes de duplicação.

## 42.5 Conceitos relacionados tratados como evidência direta

Expansões `related` podem introduzir sinais fracos.

Mitigação contratual:

- conceito exclusivamente relacionado não é elegível;
- nenhuma expansão dentro do Radar;
- validação por `direct_weight` e `inherited_weight`.

## 42.6 Confusão entre significância e interesse

Um evento significativo pode ser irrelevante para determinado pesquisador.

Mitigação contratual:

- Radar não consome Research Profile;
- Interest Engine permanece componente separado;
- razões não mencionam preferência pessoal.

## 42.7 Divergência entre catálogo e Taxonomia

Um catálogo pode referenciar IDs removidos ou alterados.

Mitigação contratual:

- `compatible_taxonomy_version`;
- configuração validada;
- erro de versão explícito;
- nenhuma correção automática.

## 42.8 Instabilidade textual das razões

Mudanças livres de texto podem quebrar comparações determinísticas.

Mitigação contratual:

- templates versionados;
- placeholders limitados;
- números com seis casas;
- testes de saída exata.

## 42.9 Domínio não canônico

Configurações podem tentar usar nomes humanos, aliases ou IDs de domínio da Taxonomia no lugar dos IDs do Radar.

Mitigação contratual:

- `RadarDomain` como enum fechado;
- oito valores canônicos explícitos;
- validação Pydantic;
- exemplos e fixtures usando os mesmos IDs;
- domínio inválido produz `EventRadarConfigError`.

## 42.10 Versão de algoritmo incompatível

Uma configuração criada para outro algoritmo não pode ser executada implicitamente pela V1.

Mitigação contratual:

- `SUPPORTED_ALGORITHM_VERSION = "1.0"`;
- comparação durante a construção;
- `EventRadarVersionError` para qualquer divergência;
- ausência de fallback ou compatibilidade implícita.

# 45. Resultado arquitetural

Com a futura implementação deste Engineering Brief, o pipeline científico possuirá uma etapa determinística de significância:

```text
Event + ConceptFingerprint
        │
        ▼
Event Radar
        │
        ├── score objetivo
        ├── nível de significância
        ├── IDs estáveis de sinais
        └── razões auditáveis
```

O Radar não substituirá:

- validação científica do Agente 113;
- representação conceitual do Concept Fingerprint;
- contexto pessoal do Research Profile;
- cálculo de interesse do Interest Engine;
- curadoria humana.

---

# 46. Princípio final

> **O Event Radar não interpreta livremente o evento. Ele aplica regras explícitas, versionadas e auditáveis sobre conceitos canônicos já produzidos pelo Concept Fingerprint.**

Essa limitação preserva:

- determinismo;
- separação de responsabilidades;
- ausência de inferência oculta;
- reprodutibilidade;
- explicabilidade científica.
